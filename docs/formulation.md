# 问题定义与系统边界（Formulation）

## 核心定位：多路直播监控

需要同时关注十余路乃至数十路直播间时，人无法同时观看多路画面或收听多路混音。`bilibili-live-monitor` 将直播转化为结构化、可追溯、可导出的房间时间线，供巡检、研究与归档使用。

当前界面聚焦文本信号。浏览器中的静音视频流是内部采音载体；看板不展示视频、不做图像理解，也不提供音频回放。

## 从双源输入到统一Item

每个房间在独立Chrome页面中运行，采集两类实时输入。

主播语音通过Web Audio `AudioWorklet`读取该房间独立的16kHz PCM，默认30秒切片，经有界队列送入常驻本地Qwen3-ASR-1.7B/MLX进程共享串行识别。每段转写生成一个item，保留时间窗口、处理状态与来源。

观众弹幕直接复用该网页已有的WebSocket连接。后端解码普通、zlib与Brotli包，每条弹幕生成一个item，不额外建立弹幕连接。

两类item按事件时间混合在每房间时间线中。弹幕采用服务器事件时间，转写采用音频窗口结束时间；识别有处理延迟，因此到达时间与事件时间可能不同。类型与状态始终可区分，不能把观众弹幕当作主播语音。

完整segments、timeline与SSE事件持久化到SQLite。前端只显示最近20段识别数据和80条item，不截断数据库历史；`GET /api/export`支持按房间导出混合JSONL。

## 有效性与失败表达

音频窗口须满足源音轨有效、音频覆盖率90%～120%、媒体进度至少墙钟80%、缺输入不超过100ms、源mute不超过100ms且无缓冲丢样。采集与识别失败标记为错误，不能伪装为正常silent。临时原始音频处理后删除。

弹幕来自网页实际接收的消息；断线、网页行为和协议变化都可能造成缺口，因此不承诺全量无损归档。时间线保留收到的信息与显式识别错误，不推断未收到的内容。

## 目标使用者与当前边界

目标使用者是在Apple Silicon Mac上跟踪多个B站直播间发言与观众动态的巡检、运营、研究人员，以及需要本地SQLite或JSONL供后续分析的开发者。

当前不包含视频展示、视觉理解、音频回放、关键词告警或LLM摘要；也不承诺B站以外平台、跨平台ASR或长期无人值守稳定性。这些能力应分别验证，不由文本时间线的成立直接推出。

## 无付费识别API的成本边界

系统使用本地Qwen3-ASR/MLX与现有网页连接，无需付费识别API。多路Chrome渲染、音视频解码、模型推理和直播流拉取仍消耗本机算力、内存与网络带宽。费用优势来自复用本机资源，不是没有资源成本。

## 当前验证水平

已在本机配置30路、队列60，验证30路各至少两个30秒有效窗口，包含播放器停顿后的恢复。ASR同段重试与崩溃恢复通过离线测试验证，不能将其写成本次实测发生过的故障。几分钟累计有效窗口不能推出无间隙或长跑保证。
