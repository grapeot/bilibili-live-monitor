# 直播过程与复盘趋势

目标是把指定房间、指定时间范围的已有数据生成可追溯的四图报告。直播中可随时运行，也可用于已结束的场次。只读现有 SQLite，不连接网站、浏览器、模型或控制面，不暂停录制。每次输出都是独立冻结快照，不是自动刷新看板。

## CLI

在已安装项目的 Python 环境中执行；`bili-live` 与 `python -m bilibili_live_monitor` 等价。

```bash
bili-live trends build \
  --db /private/run/monitor.sqlite3 \
  --room 123456 \
  --since '2030-01-01T10:00:00+08:00' \
  --until '2030-01-01T13:00:00+08:00' \
  --timezone Asia/Shanghai \
  --bin-seconds 300 \
  --title '直播趋势' \
  --output /private/reports/session_20300101

bili-live trends verify --output /private/reports/session_20300101
```

`--until` 省略时冻结到调用时刻。起止时间必须带时区，范围为左闭右开；显示时区独立设置。房间号必须是数据库使用的规范数字ID，不接受短链或自动换房。桶宽默认300秒，可设60～3600秒；桶按Unix时间格点对齐，首尾可不满一个桶。`--gap-seconds` 默认60秒，可调整长时间无业务包的可疑缺口阈值。输出目录必须不存在，后续分析另选目录，不覆盖上次证据。

成功输出 JSON 和退出码0；失败输出包含异常类型的JSON到stderr并退出2。`build` 成功前会自动执行同一套 `verify`；额外 `verify` 不读源库，可以在源库持续增长或不再可用后复核该次报告。

## 四图口径

- 入场流量：每桶按有效UID去重。同一人跨桶会重复出现；整个范围的去重人数另列。匿名入场仅留事件计数，不猜身份。它不是全房间在线人数，也不是平台完整UV。
- 送礼频次：同订单/事件合并，同一订单多个盲盒结果只计一次；包括免费礼物、SC与上舰。不按件数、金额、COMBO累计消息计次。
- 关注总数：`ROOM_REAL_TIME_MESSAGE_UPDATE.data.fans` 原值阶梯线，不计算关注事件数或净增。
- 粉丝团人数：同类消息的 `data.fans_club` 原值阶梯线。没有对应字段就缺测，不填零；合法的0保留。

所有横轴使用本机接收时间，避免混用来源事件时钟。存量点间沿用上一观测值，首点之前不补值，末次推送后虚线延续；这不表示每分钟主动重新查询。存量纵轴可非零起点，图中明确标注。无业务包的空桶留空；超过阈值没有任何业务包的区间用灰带提示可能漏采，不把它断言为停播。首尾不足桶宽用空心点/浅色柱，不接到完整入场曲线上。

## 输出与验收

输出目录包含 `index.html`、`data.json`、`manifest.json`。HTML/SVG无需CDN或网络，直接浏览器打开；移动端各图内可横向滚动。JSON保留范围、显示时区、桶宽、源行ID、入场UID、订单去重键、原始存量观测、聚合和缺口。它含真实身份信息，只保存到私有目录，不提交公开仓库。

验收要求：CLI退出0且verify通过；四项图表齐全；指定房间/范围隔离；去重和分桶计数可重算；缺测、零值、匿名和首尾不完整桶区别明确。抽查源库行ID和至少一个原始存量样本；首次使用或修改渲染后，检查桌面与移动宽度的实际页面，无页面级横向溢出。没有数据也应正常出报告，并明确显示无观测，不能伪造曲线。没有原始业务消息的历史场次不能从录像推断关注、粉丝团或礼物数据。

分析时将采集缺口、数量变化和因果解释分开。不能仅凭曲线把增长归因于某句欢迎、某首歌或某笔礼物。用户需要更新时再次运行到新的冻结目录；建立定时任务、发布网页、发送报告属于独立操作授权。
